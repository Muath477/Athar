# ADR-027: Bring photos in from site cameras, drones and bulk uploads

- Status: Accepted
- Date: 2026-11-20

## Context

Until now a wall map started from one photo an inspector took in the new-map flow. A heritage authority has more sources than that: fixed cameras already watching a site (usually behind an NVR), drone surveys with hundreds of nadir and oblique shots, and staff who come back from the field with a phone full of photos. Each of these should reach the same detector, the same 10-step workflow and the same specialist approval as an inspector's photo, without someone redrawing every map by hand.

Two risks come with this. A camera URL typed into the dashboard makes the server fetch an address chosen by a user, which is the classic server-side request forgery path into internal services and cloud metadata. And drone and phone photos carry GPS and faces, which the privacy rules (ADR-015) say must not be stored.

## Decision

- A new `ingest` module owns two tables, `devices` and `ingest_jobs`, and reaches the rest of the system only through the `sites`, `capture`, `mapping` and `admin` facades. It sits at the top of the module graph next to `agents`, `reports` and `watch`.
- **Devices.** A device has a kind (`fixed_camera`, `drone`, `phone`, `upload`), an Arabic name, an optional site and facade, an optional HTTP(S) snapshot URL and RTSP URL, a username, the name of an environment variable that holds its password, a capture interval, and its last capture time, status, error and photo. A fixed camera needs a site; it usually points at one facade. Reading the registry needs `read`; changing it and "capture now" need `manage_devices`. Every change is audited.
- **Camera passwords.** The database never holds a camera password. A device stores only an environment variable name that must match `SADU_CAMERA_SECRET_[A-Z0-9_]+`, and the API reports whether it is set. URLs with `user:pass@` or with query parameters such as `pwd`, `password`, `token` or `key` are rejected. We chose this over encrypting a column because it needs no key management for the hackathon, keeps secrets out of database dumps and backups, and fits how the deployment already passes secrets (compose `.env`, a secret manager in production). The cost is that adding a camera with a password needs a server restart with the new variable; rotating it does too.
- **Snapshot capture.** Most IP cameras and NVRs serve a still JPEG on an HTTP endpoint (for example Hikvision's `/ISAPI/Streaming/channels/101/picture`), so that is the main path. The fetch uses Digest authentication and falls back to Basic when the camera asks for it, follows no redirects, accepts only `image/jpeg` or `image/png`, stops reading past the capture upload limit (8 MB) and times out after 10 seconds. It is retried once with backoff through `shared/resilience.call_with_policy`.
- **RTSP.** When a device has no snapshot URL but has an RTSP URL, the server grabs one frame with `ffmpeg` (`-rtsp_transport tcp -frames:v 1`, protocols limited to `rtsp,rtp,tcp,udp`, killed after the timeout). This works only where `ffmpeg` is on the path; otherwise the capture fails with a clear Arabic message. The API image does not install ffmpeg yet, so RTSP is out of scope for the demo deployment. Credentials for RTSP go into the URL passed to ffmpeg's argument list, so they are visible to processes in the same container.
- **SSRF stance.** Only `http`, `https` and (for streams) `rtsp` are accepted. The host is resolved once, and every resolved address must be public: loopback, private, link-local, shared (100.64/10), multicast and reserved ranges are refused, and IPv4-mapped IPv6 is unwrapped first. The request then goes to the checked IP, with the original `Host` header and TLS server name, so DNS cannot change the answer between the check and the connection. Cameras usually sit on a private site network, so admins opt in with `SADU_CAMERA_ALLOWED_HOSTS`, a comma-separated list of host names and CIDR ranges (`nvr.site.local,10.20.0.0/16`). Cloud metadata addresses (`169.254.169.254`, `fd00:ec2::254`) stay blocked even when allowlisted. In demo mode `localhost` is added so the demo camera can reach the API's own demo snapshot route.
- **Jobs.** Every photo, from any source, becomes one `ingest_jobs` row: source (`camera`, `drone`, `inspector`, `upload`) and device, batch, storage key, chosen or matched site and facade, status (`queued`, `analysing`, `needs_facade`, `done`, `failed`), attempts and next attempt time, Arabic error, photo metadata and the resulting map. A camera that cannot be reached still leaves a failed job, so the device history shows every attempt.
- **Worker.** An in-process worker claims due jobs with `FOR UPDATE SKIP LOCKED`, `SADU_INGEST_CONCURRENCY` at a time (default 2), and is woken as soon as a capture or upload queues work; a loop also wakes it every 30 seconds for retries. Jobs left in `analysing` by a restart go back to the queue at startup. A transient failure is retried after 1 and then 2 minutes; the third failure marks the job failed. A rejected photo (unreadable, unusable for the detector) fails at once. A person can retry a failed job that still has its photo. A second loop captures every active camera whose last capture is older than its interval, or `SADU_CAMERA_INTERVAL_H` (default 24) when it has none; `0` turns scheduled capture off and "capture now" still works.
- **Processing order.** For each job the worker:
  1. reads EXIF GPS and `DateTimeOriginal` (with `OffsetTimeOriginal` when present) from the original bytes and keeps them as job metadata;
  2. converts HEIC to JPEG if `pillow-heif` is installed; otherwise HEIC uploads are rejected up front with an Arabic message telling the user to export JPEG;
  3. runs capture's `process_upload` (face blur, EXIF strip, resize), stores the result and deletes the original;
  4. picks the facade: the one chosen at upload, else the device's facade, else GPS matching, else stops at `needs_facade` for a person to assign;
  5. creates a draft map through `mapping.prepare_wall`, `detect_damage` and `save_map`, the same calls `POST /maps` makes, using the whole frame as the wall outline.
- **GPS matching.** Sites whose boundary lies within 60 m of the photo position are candidates (`sites.find_sites_near`); the closest by site centre wins. The photo position is converted to east/north metres from the site origin, matching the facade map's axes (+X east, −Z north). Among the facades whose outward side faces the photo position, the one with the nearest base edge wins; if none faces it, the nearest edge wins. Drone photos go through the same rule, whether nadir or oblique, and are tagged `drone` in the job and on the map.
- **Bulk upload.** `POST /ingest/uploads` (permission `survey`) takes 1 to 30 files of up to 8 MB each, an optional site, facade or device, and returns a batch with one job per file. `GET /ingest/batches/{id}` reports progress. The dashboard page `/dashboard/uploads` polls it, links each finished photo to its map, lets the user retry failed ones and pick a facade for photos that need one.
- **Provenance.** `damage_maps` gained nullable `source` and `source_label`. Maps from the new-map flow are marked `inspector`; ingested maps carry `camera`, `drone` or `upload` and the device name. Older maps keep both empty. The map page and map cards show the source.
- **Inspector phones.** Phones are not auto-registered per inspector: photos from an inspector's phone arrive through `/dashboard/maps/new` or `/dashboard/uploads` and are attributed to the signed-in user. A `phone` device can still be registered for a shared site phone; its uploads are marked `inspector`.
- **Demo.** With `SADU_DEMO_MODE=true`, `python -m sadu.cli seed --pack demo` registers a fixed camera on the demo building's north facade whose snapshot URL is `http://localhost:8000/api/v1/ingest/demo-snapshots/north-crack.jpg`. That route serves files from `region-packs/demo/test-photos/` only in demo mode, so the camera flow works offline. Tests replace the camera client with a fake.

## Alternatives

- **Encrypting the password column** with a key from the environment. Rejected for now: it still needs a key in the environment, plus rotation and a migration path, for no gain over storing the variable name.
- **A separate ingestion service or a queue (Redis, SQS).** Rejected by ADR-008: the job table and an in-process worker are enough for tens of cameras and survive restarts.
- **Streaming RTSP continuously.** Rejected: damage on earthen walls changes over days, so one frame a day is enough, and a still endpoint avoids keeping streams open.
- **Matching facades by GPS heading.** Phone compass headings in EXIF are often missing or wrong near metal; position against the facade footprint is good enough at 60 m and works for drones.

## Consequences

- Cameras on a site network need an explicit allowlist entry; a typo in a URL cannot reach internal services.
- Drone and phone photos lose their GPS and faces before they are stored, but the job keeps the GPS reading and capture time as metadata so a reviewer can see where a photo came from. That metadata records where staff or a drone stood, not visitors, and it stays on the job record.
- The original upload exists in object storage only until the worker processes it, usually seconds.
- Every ingested map is a draft and goes through the specialist's field inspection and approval like any other.
- Running more than one API process would run more than one worker. `SKIP LOCKED` keeps jobs from being processed twice, but scheduled camera captures would be duplicated; that needs a lease before scaling out.
